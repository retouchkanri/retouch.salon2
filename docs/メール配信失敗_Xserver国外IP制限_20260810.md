# メール一斉配信が全件失敗する不具合 — 対応報告（2026-08-10）

## ご報告いただいた事象
2026-08-09 19:16 の一斉配信「Retouch【自動配信】／無料登録期間の終了と継続についてのお知らせ」が、対象 1,198 名に対して **配信0件 / 失敗114件 / 未送信1,081件** となり、配信中のまま停止しました。

同日、送信元メールアドレスを `info@retouch.salon`（Xserver で取得したドメイン）へ変更しています。

## 原因

**Xserver のメールサーバーが、Vercel（本番サーバー）のIPアドレスからの送信を拒否していました。**

データベースに記録されていた失敗114件のエラーは、すべて完全に同一でした。

```
554 5.7.1 <ec2-52-205-230-6.compute-1.amazonaws.com[52.205.230.6]>:
Client host rejected: Access denied
```

`52.205.230.6` は AWS の **us-east-1（米国バージニア）** のIPアドレスです。`vercel.json` にリージョン指定が無かったため、本番の処理が Vercel の既定リージョン（米国）で実行され、そこから Xserver へ接続していました。

Xserver には **「国外IPアクセス制限」** という機能があり、日本国外のIPアドレスからのアクセスを既定で遮断します。これに抵触したため、送信が全件拒否されていました。

### 調査で確認した事実

| 確認項目 | 結果 |
| --- | --- |
| DNS（MXレコード） | `retouch.salon` → `sv17168.xserver.jp` ✅ 設定は正しい |
| SPFレコード | `v=spf1 +a:sv17168.xserver.jp ... include:spf.sender.xserver.jp` ✅ 設定済み |
| SMTP認証（日本のIPから） | `235 Authentication successful` ✅ ID・パスワードは正しい |
| 宛先受理（日本のIPから） | `250 2.1.5 Ok` ✅ 送信できる状態 |
| 宛先受理（米国のIPから＝本番） | `554 5.7.1 Client host rejected` ❌ 拒否 |

**同じID・パスワード・同じ宛先でも、日本のIPからは成功し、米国のIPからは拒否される**ことを確認しました。つまり設定ミスではなく、接続元の国による遮断です。

なお、検証に使用した日本側のIP（`static.140-45-179-103.webhorizon.net`）は**データセンターのIP**です。これが受理されたことから、Xserver の遮断は「クラウド事業者の遮断」ではなく**純粋に国（日本国外か否か）による遮断**であることが確認できました。したがって、送信元を日本国内リージョンへ移せば解消します。

### なぜ事前に気づけなかったか
従来の疎通確認スクリプト `scripts/smtp-test.ts` は**手元のPC（日本）から実行**するため必ず成功し、本番の失敗を再現できませんでした。「ローカルでは送れるのに本番だけ全滅する」という形の障害です。

さらに、一般的な疎通確認である nodemailer の `verify()` は **接続と認証までしか行いません**。今回の拒否は認証成功後の `RCPT TO`（宛先指定）の段階で発生するため、`verify()` では「正常」と判定されてしまいます。

## 対応内容

### 1. 送信元リージョンを東京に固定（根本対応）

`vercel.json` で本番の実行リージョンを **`hnd1`（東京）** に固定しました。これにより送信元IPが日本国内となり、国外IP制限に抵触しなくなります。

```json
{
  "regions": ["hnd1"],
  "crons": [{ "path": "/api/cron/newsletters", "schedule": "0 15 * * *" }]
}
```

配信処理の各ルート（`member-messages/[id]/send`、`cron/newsletters`）にも `preferredRegion = "hnd1"` を明記し、設定が意図せず戻された場合にも気づけるようにしています。

**副次的な改善:** データベース（Supabase）は AWS ソウルリージョンにあります。従来は米国のサーバーから太平洋を越えて接続していたため、今回の変更で管理画面・マイページ全体の応答速度も改善します。

### 2. 障害の判定漏れを修正（被害拡大の防止）

`isInfrastructureSendError()`（`src/lib/memberMessages.ts`）が今回のエラーを認識できず、**サーバー全体の障害を「宛先ごとの個別失敗」と誤判定**していました。その結果、114名分が復旧不能な `failed` 状態へ次々と焼き払われていました。

この関数は 2026-08-03 の Gmail 障害を受けて「基盤障害なら送信を中断して保留する」ために作られたものですが、今回の新しいエラー文言が判定条件から漏れていました。

送信元ホストの拒否・リレー拒否・差出人拒否・ブラックリスト掲載を基盤障害として追加しました。あわせて、**宛先固有の拒否を先に判定する**ガードを追加しています（`554 5.7.1` は「接続元の拒否」と「宛先の拒否」の両方で使われるため、取り違えると特定の1件が毎回先頭に来て配信全体が永久に止まる「毒薬行」になります）。

検証は `tests/notifyErrors.test.ts` に追加しました（実際に本番で記録されたエラー文字列をそのまま使用）。

### 3. 本番から検証できる診断機能を追加（再発防止）

本番環境そのものから疎通を確認する診断APIを追加しました。**メールは1通も送信しません**（`RCPT TO` まで進めた後 `RSET` で中断するため、`DATA` を送りません）。

```
GET /api/admin/diagnostics/smtp           … 自ドメイン宛で検証
GET /api/admin/diagnostics/smtp?to=x@y.z  … 外部宛でリレー許可まで検証
```

管理者（`messages.manage` 権限）でログインした状態でアクセスしてください。以下を返します。

- 実行リージョンと**送信元IPアドレス・国**
- SMTP の各段階（接続 / EHLO / 認証 / MAIL FROM / **RCPT TO**）の応答
- 失敗時は日本語の原因推定
- 送信元が国外の場合の警告

手元から実行する場合は `npm run smtp:probe`（`npm run smtp:probe you@example.com` で外部宛リレーまで検証）。ただし手元は日本のIPのため、**本番の可否は必ず診断API側で確認**してください。

## 復旧手順

1. 本ブランチをデプロイする
2. `/api/admin/diagnostics/smtp` を開き、`egressCountry` が `JP`、`vercelRegion` が `hnd1`、`verdict` が ✅ であることを確認する
3. 管理画面の配信詳細で **「失敗分を再送」** を押す（`failed` 114件が `pending` に戻ります）
4. **「配信を続ける」** を押す（または毎日 15:00 UTC の cron が自動で続きを送ります）

## 補足（ご確認ください）

`MAIL_FROM` は `info@retouch.salon` に変更されていますが、`CONTACT_EMAIL` / `CONTACT_RECIPIENTS` は `info@retouch-members.com` のままです。そのため全メールの返信先（Reply-To）と署名の「お問い合わせ:」欄が引き続き旧ドメインを指しています。旧アドレスを受信し続けるのであれば問題ありませんが、移行される場合は環境変数の更新が必要です。

## もし東京リージョンでも拒否された場合

調査結果からは解消する見込みですが、万一 `/api/admin/diagnostics/smtp` が `hnd1` でも拒否を返す場合は、Xserver 側で制限を解除してください。

サーバーパネル → **国外IPアクセス制限設定** → **メール** → 対象ドメイン → **解除**
